Name and identity

Decided 2026-10-21: the product is called TRIDENT. The candidates below are kept as the record of the earlier choice. Three name candidates. Tarazu is recommended and used on this page as a working name. None of the three has been checked against trademarks or domains yet; that search (IP India classes 9 and 42, plus .com/.in domains) must happen before you commit. Until then the app keeps reading the name from brand.ts, so changing it is one line.

Tarazu तराज़ू · the shopkeeper's balance scale

Says "fair measure" and "stock in balances stock out" in a word every Indian retailer knows. Short, ownable, easy to say on a support call.

TRIDENT TRIDENT

Mark: a balance beam with a marigold pivot, drawn on a 40-unit grid with round caps. The marigold dot is the only place the accent appears in the brand, and it returns in the product as the "scanner ready" signal.

Colour

One brand colour, one accent, cool neutrals and four status colours. Every text pairing meets WCAG 2.2 AA (4.5:1). Status is never shown by colour alone; every badge carries a word.

IBM Plex Sans for everything, Plex Mono for SKUs, barcodes and document numbers. Plex has true tabular figures, so rupee columns line up, and a Devanagari sibling ready for a Hindi interface. Self-host the font files in production.

Responsive behaviour

Desktop-first, usable on tablet and phone (PRD 2.2, AC-19). The counter screens are designed for a 10-inch tablet in landscape.

Rules

  • The page body never scrolls sideways; only a table container may.
  • Primary action stays visible: sticky footer on phones, top-right on desktop.
  • Touch devices (pointer: coarse) get 44 px minimum controls automatically.
  • Charts are capped at two on the dashboard; on phones they become a single number with a sparkline.

Column priority (tables)

  • Always: identity (name/number), status, the one number the screen is about.
  • Tablet hides: category, brand, created-by, secondary dates.
  • Phone: card shows title, status badge, two key values; tap opens detail.

Accessibility requirements

Target WCAG 2.2 level AA. These are acceptance criteria for every screen built from B2 on, checked with axe in CI and by a keyboard-only pass before each stage closes.

Perceivable

  • Text contrast ≥ 4.5:1, controls and focus ≥ 3:1 (tokens already meet this).
  • Status never by colour alone: badge text, row stripe plus a word.
  • Images have alt text from the product's alt field; decorative thumbs use empty alt.
  • Text resizes to 200% without loss; layout reflows at 320 px.

Operable

  • Every action reachable by keyboard; visible 2 px focus ring on all controls.
  • Skip link to main content; logical tab order; no keyboard traps in dialogs (focus returns to the trigger).
  • POS shortcuts: F2 scan/search, F4 customer, F8 discount, F9 pay, Esc cancel. Shortcuts shown on the buttons.
  • Touch targets ≥ 24 px everywhere (WCAG 2.5.8), ≥ 44 px on counter screens.
  • Motion is decorative only and stops under reduced-motion.

Understandable

  • Every input has a visible label; required marked with * and in the label text for screen readers.
  • Errors say what is wrong and how to fix it, sit under the field, and are linked with aria-describedby; a summary at the top on submit.
  • Destructive actions confirm with a dialog that names the object and the consequence.
  • lang="en-IN" on the document; Hindi strings get lang="hi".

Robust

  • Native elements first (button, select, table, dialog). ARIA only where HTML has no equivalent (tabs, live regions).
  • Scan results, toasts and POS totals update an aria-live="polite" region; errors use role="alert".
  • Tables use th scope and aria-sort.
  • Tested with NVDA + Chrome and VoiceOver + Safari before launch (B7).
